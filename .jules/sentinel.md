## 2024-05-24 - Remove Hardcoded Passwords in AWS Templates
**Vulnerability:** Found hardcoded user creation (`rstudio`) with a hardcoded password (`rstudio`) inside CloudFormation UserData scripts (`R/AWS/sagemaker_stack.txt` and `R/AWS/template1`). This is a critical security risk because anyone deploying this template would create an instance with a known, default password, potentially exposing it to unauthorized access if port 8787 is open.
**Learning:** Hardcoded credentials are often used in demo/quickstart templates for convenience, but they violate security best practices and can lead to compromised instances.
**Prevention:** Instead of hardcoding passwords, use secure alternatives. Since this is an EC2 instance that already uses SSH keys for access, we should configure the `rstudio` user to use a randomly generated password, or better yet, rely on AWS Systems Manager Parameter Store or Secrets Manager, or simply enforce that the password must be changed. As a quick fix that doesn't overcomplicate the template, we can generate a random password during setup and log it locally or let the user connect via SSM/SSH and set the password themselves, or utilize an SSH tunnel with key-based authentication. Given the context (RStudio server requires password auth by default), generating a random password during user-data execution and printing a message to the logs or storing it securely is better, but since `R/AWS/template1` outputs an SSH tunnel command (`Value: !Sub "ssh -L 8787:localhost:8787 -i ${KeyName}.pem ec2-user@${Instance.PublicDnsName}"`), the instance is expected to be accessed via port forwarding rather than direct public access. Even so, a random password is much safer.
